Check a Lean source file with the project's Lean (`lake env lean` on the file's current staged revision). Returns success/fail status.

On success: returns "success" status plus `status_detail`:
- `final_theorem_success` means the file checks, no `sorry` remains, and the target theorem is complete; the final gate (below) then ran.
- `compile_success_nonfinal` means the file checks but is not yet a finished theorem, usually because `sorry` placeholders remain.
On failure: returns "fail" status with Lean's error messages and their line numbers.

Usage:
- `filePath` is a .lean file within the workspace (absolute or workspace-relative). The staged revision of the file is checked; the file on disk is not changed.
- Helper modules under `CaseStudies/` that the file imports are rebuilt first when they changed.
- A check times out after 20 minutes by default (OPENCODE_LEAN_TIMEOUT_MS) and reports a tool error on timeout.
- Use it after a coherent edit to see Lean's errors; for step-by-step tactic work use `lean_session`.
- `lean_check` returns error messages only. It does not show proof goals; read them with `lean_session`.
- When the target theorem is complete, the tool also runs the final gate before marking the revision committable: frozen statement files unchanged, no forbidden tokens (`sorry`, `admit`, `axiom`, `unsafe`, `implemented_by`, `@[extern]`, debug options, `#eval`, `run_cmd`, `elab`, …), the module builds, the solution has exactly the frozen statement's type, and `#print axioms` lists only `propext`, `Classical.choice` and `Quot.sound` (so `native_decide` is rejected). `status: final_gate_rejected` means the file checks but the gate failed; repair the listed reason(s) and run `lean_check` again. The rejected revision is not finalized.
